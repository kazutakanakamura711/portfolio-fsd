# 開発・運用ルール

このプロジェクトは、`develop` を開発用ブランチ、`main` を本番反映用ブランチとして運用します。

## ブランチ運用

通常の開発は次の流れで行います。

1. `develop` を最新化する。
2. `develop` から作業ブランチを作成する。
3. 実装と動作確認を行う。
4. 作業ブランチをリモートへプッシュする。
5. `develop` 向けにPull Request（PR）を作成する。
6. レビューで問題がないことを確認してから `develop` にマージする。
7. リリース時に `develop` を `main` へマージし、本番環境（Vercel）を確認する。

`main` と `develop` への直接コミット・直接プッシュは行いません。

### ブランチ名

ブランチ名は、コミット種別と同じ接頭辞を使った次の形式にします。

```text
<type>/<short-description>
```

- 小文字の英語とハイフン区切り（ケバブケース）を使う。
- 説明は変更内容が分かる2〜5語程度にする。
- 1ブランチには1つの目的だけを含める。
- 日本語、空白、アンダースコア、作業経緯（例：`from-main`）を含めない。

例：

- `feat/add-lp-section`
- `fix/lp-github-link`
- `refactor/projects-api-client`
- `docs/project-guidelines`
- `chore/update-dependencies`
- `test/projects-filter`
- `style/format-markdown`

緊急の本番修正だけは、例外として `hotfix/<short-description>` を使用できます。

## コミットメッセージ

コミットメッセージは Conventional Commits に従います。

| プレフィックス | 用途                     |
| -------------- | ------------------------ |
| `feat:`        | 新機能追加               |
| `fix:`         | バグ修正                 |
| `chore:`       | 設定変更・ライブラリ更新 |
| `refactor:`    | リファクタリング         |
| `docs:`        | ドキュメント             |
| `test:`        | テスト追加・修正         |
| `style:`       | フォーマット修正         |

例：

```text
feat: LPにGitHubリンクを追加
fix: ページごとのナビゲーション表示を修正
docs: 開発運用ルールを追加
```

1つのコミットには、できるだけ1つの目的だけを含めます。無関係な変更を同じコミットに混ぜないでください。

## Pull Request

- PRのベースブランチは原則 `develop` にする。
- PRのタイトルと本文は日本語で記載する。
- PR作成時は作成者本人をアサインする。
- PR本文には「概要」「変更内容」「確認内容」「レビューしてほしい点」を記載する。
- CIが成功し、レビューで問題がないことを確認してからマージする。
- レビューなしで自己判断によるマージは行わない。

### PR本文テンプレート

```markdown
## 概要

<!-- 変更の目的を簡潔に記載 -->

## 変更内容

-

## 確認内容

- [ ] `npm run test:unit`
- [ ] `npm run build`
- [ ] `npm run lint`
- [ ] ブラウザでの動作確認

## レビューしてほしい点

<!-- 特に確認してほしい点があれば記載 -->
```

## リリース

`develop` で変更を確認した後、`main` へマージします。マージ後はVercelのデプロイ結果と本番サイトの主要ページを確認します。

## MicroCMS

- MicroCMSのスキーマ定義は `cms-schemas/` に保存する。
- スキーマを変更した場合は、必要に応じて `npm run generate:types` を実行し、生成型と実装の整合性を確認する。
- 現在の統合コンテンツAPIは `projects` で、`type` に `application`、`work`、`wordpress`、`lp` を設定する。
- APIのフィールド変更後は、公開状態、APIプレビュー、実サイト表示を確認する。
- コンテンツAPIやフィールドを削除する前に、参照コード、スキーマのバックアップ、公開データを確認する。
